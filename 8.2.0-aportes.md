# Release 8.2.0 – Inventario QR, Transferencias concurrentes, Gestión de Activos Fijos y Bajas SABS

## Resumen de la Versión

Esta versión incorpora los siguientes módulos y funcionalidades del sistema **Activa360**:

1. **Inventario QR (Guillermo Daza)**: nuevos endpoints de escaneo y registro de inventario, modelo `InventoryRecord` con restricción de concurrencia `@@unique([campaignId, assetId])`.
2. **Transferencias Concurrentes (Guillermo Daza)**: refactor de `TransferAssetService` usando transacciones con bloqueo pesimista `SELECT FOR UPDATE` para prevenir race conditions. FK `Transfer.assetId → Asset.id`.
3. **Módulo Inventario y Ciclo Patrimonial SABS (Josefina Rojas)**:
   - **Feature 1 — Gestión de Activos Fijos y Control de Estados SABS (Mediana / FSD-UC-001)**: alta patrimonial (`POST /activos`) validando unicidad de código SABS/QR, descripción, categoría, fecha de adquisición, valor histórico y estado inicial (`DISPONIBLE` / `ACTIVO`). Consulta flexible con filtros por estado, código y unidad (`GET /activos`), detalle con historial de trazabilidad (`GET /activos/{id}`) y transición controlada de estados normativos (`PATCH /activos/{id}/estado`) con matriz SABS y bloqueo de reactivación indebida sobre el estado terminal `Dado_De_Baja`.
   - **Feature 2 — Diagnóstico Técnico Previo a Baja y Soporte de Restauración Condicional (Mediana / FSD-UC-003)**: emisión de informe técnico pericial (`POST /activos/{id}/diagnosticos`) con correlativo único, causales SABS (*obsolescencia, deterioro irreparable, siniestro, incompatibilidad técnica, hurto/robo*), dictamen, recomendación y evidencia documental. Si dictamina baja, transiciona automáticamente el activo a `APTO_PARA_BAJA` y deja el diagnóstico en estado `VIGENTE` para habilitar el workflow de bajas. Listado y consulta individual (`GET /diagnosticos` y `GET /diagnosticos/{id}`) con filtros por estado y activo. Integración con `POST /bajas` (consumo de diagnóstico a `UTILIZADO_EN_BAJA`) y `POST /bajas/{id}/rechazar` (restauración condicional del informe técnico a `RESTAURADO` y del activo a revisión técnica).
4. **Módulo Compliance: Bajas SABS (Rita Nina)**:
   - **Feature 1 — Filtros en listado de Bajas (`GET /bajas`)**: filtrado individual y combinado por `estado` (`INICIADA`, `APROBADA`, `RECHAZADA`), término del activo (búsqueda insensible a mayúsculas por ID, código QR o nombre) y rango temporal (`fechaDesde` y `fechaHasta`).
   - **Feature 2 — Paginación en `GET /bajas`**: soporte para `page` (mín. 1, default 1) y `limit` (mín. 1, máx. 100, default 10), con respuesta estandarizada `{ data: Baja[], meta: { total, page, limit, totalPages } }`.
   - **Feature 3 — Comentario al rechazar (`POST /bajas/:id/rechazar`)**: validación del campo obligatorio `motivoRechazo` (mínimo 5 caracteres), verificación de estado `INICIADA`, cambio a `RECHAZADA` persistiendo el motivo en base de datos (`Baja.motivoRechazo`), restauración del activo a revisión técnica (`Dañado` u `Obsoleto`) y retorno de la entidad actualizada.
   - **Integración Frontend**: página de Bajas (`frontend/src/pages/Bajas.tsx`) con barra de filtros, controles de paginación interactiva, modal de confirmación de rechazo con validación de motivo y visualización del motivo en tarjetas con estado `RECHAZADA`.

## Contrato OpenAPI (`openapi.json`)

Los nuevos endpoints y DTOs están completamente documentados con decoradores de `@nestjs/swagger` y validados con Spectral CLI (**0 errores y 0 advertencias**):
- `POST /activos`: registro de bien patrimonial con código SABS/QR único; DTO `RegisterAssetDto`, respuestas `201`, `400`, `409`.
- `GET /activos`: consulta de bienes patrimoniales con filtros `estado`, `codigo`, `unidad`; respuesta `AssetResponseDto[]`.
- `GET /activos/{id}`: consulta detallada del activo con trazabilidad histórica de cambios de estado e informes de diagnóstico técnico asociados.
- `PATCH /activos/{id}/estado`: transición controlada de estados normativos SABS; DTO `ChangeAssetStatusDto`, respuestas `200`, `400`, `404`, `409`.
- `POST /activos/{id}/diagnosticos`: emisión de informe pericial previo a bajas; DTO `CreateDiagnosticoDto`, respuestas `201`, `400`, `404`, `409`.
- `GET /diagnosticos`: consulta de informes técnicos con filtros `estado` y `activo_id`; respuesta `DiagnosticoResponseDto[]`.
- `GET /diagnosticos/{id}`: consulta individual de informe pericial por UUID; respuestas `200`, `404`.
- `GET /bajas`: parámetros de consulta `estado`, `activo`, `fechaDesde`, `fechaHasta`, `page`, `limit`; respuesta tipada `PaginatedBajasResponseDto`.
- `POST /bajas`: inicio de trámite de baja que consume el diagnóstico `VIGENTE` a `UTILIZADO_EN_BAJA` y transiciona el activo a `En_Proceso_Baja`.
- `POST /bajas/{id}/rechazar`: parámetro de ruta `id`, cuerpo de solicitud tipado `RejectBajaDto` (`motivoRechazo`), restauración condicional del diagnóstico técnico a `RESTAURADO` y del activo a revisión técnica; respuestas `200`, `400`, `404`.
- `POST /bajas/{id}/aprobar`: aprobación definitiva de la baja y pase del activo a estado terminal `Dado_De_Baja`.
- Flujo de CI automatizado: `.github/workflows/openapi-ci.yml` ejecutando exportación, control de drift (`git diff --exit-code openapi.json`) y linter Spectral con `.spectral.yaml` (**0 errores, 0 warnings**).

## Instalación y Ejecución
```bash
npm install
npx prisma db push       # sincroniza esquema con campo motivoRechazo
npm run build            # compila backend NestJS
npm run openapi:export   # exporta contrato OpenAPI
npm test                 # ejecuta suite de pruebas Jest
npm run start:dev        # arranca API en localhost:3000

# Frontend
cd frontend && npm install && npm run build && npm run dev
```
